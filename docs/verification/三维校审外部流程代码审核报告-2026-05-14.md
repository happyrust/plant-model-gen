# 三维校审外部流程代码审核报告（2026-05-14）

## 审核范围

本次按 `backend-review-worker` 与 `frontend-review-worker` 的口径，重点审核“默认外部流程驱动”下三维校审链路：

- 后端：`plant-model-gen/src/web_api/platform_api/workflow_sync.rs`
- 后端类型/API：`plant-model-gen/src/web_api/platform_api/types.rs`
- 前端 workflow bridge：`plant3d-web/src/components/DockLayout.vue`
- 前端 postMessage 协议：`plant3d-web/src/components/review/embedPostMessageBridge.ts`
- 前端 review store：`plant3d-web/src/composables/useReviewStore.ts`
- 前端 API adapter：`plant3d-web/src/api/reviewApi.ts`
- 外部流程模式：`plant3d-web/src/components/review/workflowMode.ts`

未运行自动化测试。依据项目约束，本次为静态代码审核与契约一致性检查。

## 总体结论

代码主链路已经切到外部流程驱动：前端默认 `external`，PMS 通过 `pms.workflow_pre_action` / `pms.workflow_changed` 驱动 `workflow/verify` 与 `workflow/sync`，后端在未显式声明内部模式时也按 external 处理。

但当前实现存在几处需要尽快收敛的问题：外部模式下后端 owner 校验被整体跳过、postMessage bridge 默认不限制来源、前端外部同步成功后未更新本地 `currentTask`，以及旧验证报告仍保留历史 return 批注门禁语义（已加历史说明）。

## 发现的问题

### P0：外部模式默认跳过 owner 校验，`verify` 注释与实际权限边界不一致

证据：

- `workflow_sync.rs` 中默认 `workflow_mode` 为 `None` 时按 external 处理。
- `ensure_owner_matches()` 在 external workflow 下直接 `return Ok(())`。
- `verify_workflow_handler` 注释仍写明第 4 步会做 owner 校验。

影响：

- 默认 external 已是主路径时，`verify` / `sync` 对当前节点负责人不再做后端 owner 校验。
- 如果调用方持有有效 token 并能构造请求，就可能绕过“当前节点负责人”约束。
- 现有注释和部分测试期望仍暗示会返回 `OWNER_MISMATCH`，与代码行为不一致，后续维护容易误判安全边界。

建议：

- 明确产品契约：external 模式是否完全信任 PMS 的 S2S token。
- 如果仍需后端兜底，external 模式至少应校验 token claims 中的 `user_id/role` 与当前节点或 PMS actor 一致。
- 如果决定信任 PMS，则更新注释、测试和接入文档，避免继续声称 verify 做 owner 校验。

### P1：postMessage bridge 默认不校验来源，且响应目标使用 `*`

证据：

- `DockLayout.vue` 调用 `attachEmbedPostMessageBridge()` 时未传 `trustedOrigins`。
- `embedPostMessageBridge.ts` 只有在 `trustedOrigins` 非空时才检查 `event.origin`。
- ack / synced 响应都使用 `postMessage(..., '*')`。

影响：

- 嵌入页中持有 `user_token`，任意父窗口或同页面获得 frame 引用的脚本都可发送 `pms.workflow_pre_action` / `pms.workflow_changed`。
- 这会触发自动保存、`workflow/verify`、`workflow/sync` 等外部流程动作。
- 在真实 PMS 场景中应尽量把消息来源限定到 PMS 域名或 token claims 中的可信来源。

建议：

- 在 embed token claims 或运行配置中加入允许的 PMS origin。
- `DockLayout.vue` 注册 bridge 时传入 `trustedOrigins`。
- 响应时使用 `event.origin`，不要使用 `*`。
- 为“未配置 trustedOrigins 时拒绝 workflow mutation”补充测试。

### P1：`fill_actor_from_claims` 优先保留请求体 actor，未强制绑定 JWT claims

证据：

- `fill_actor_from_claims()` 注释说明显式传 actor 时保留 `id/roles`。
- 只有请求体未传 actor 时才从 JWT claims 推导 actor。
- 前端 `reviewVerifyWorkflow()` 和 `reviewWorkflowSyncMutation()` 都会发送 actor。

影响：

- 只要请求体传了 actor，后端就不会用 token claims 覆盖 actor。
- 结合 external 模式 owner 校验跳过，token 的用户身份无法作为强约束。
- 这与 `verify` 注释“actor 自动从 token claims 推导”不一致。

建议：

- 生产路径优先使用 token claims 覆盖 actor；请求体 actor 只作为 debug 或展示名补充。
- 若保留请求体 actor，至少校验 actor.id / roles 与 claims 一致。
- 增加“token 为 SJ、请求体 actor 为 JH 时必须失败”的回归验证。

### P2：前端外部同步成功后没有刷新 `reviewStore.currentTask`

证据：

- `applyExternalWorkflowChange()` 调 `reviewWorkflowSyncMutation()` 后只执行 `userStore.loadReviewTasks()`。
- 随后从 `userStore.reviewTasks` 找到 refreshed task，并仅把状态返回给 bridge ack。
- 没有调用 `setCurrentTask(refreshed)` 或直接更新 `currentTask.value`。

影响：

- 父 PMS 收到的 ack 可能是新的 `status/currentNode`，但嵌入页本地工作台仍持有旧 `currentTask`。
- 后续同一 iframe 内再次发起 `pre_action` / `workflow_changed` 时，前端可能基于旧 currentNode 推导 nextStep，产生 `missing_next_step`、错误默认节点或 UI 状态滞后。

建议：

- 成功 sync 后同步更新 `currentTask`，并重新加载确认记录/历史。
- 增加前端测试：`pms.workflow_changed(return)` 后本地 `currentTask.currentNode/status` 与后端返回一致。

### P2：前端仍会本地推导 `nextStep`，与“外部流程驱动”契约不一致

证据：

- `resolveExternalWorkflowNextStep()` 在 `payload.nextStep` 缺失时，会按本地 `currentTask.currentNode` 与 `payload.targetNode/action` 推导下一节点。
- `active` 会默认推导到 `jd`，`return` 会默认推导到 `sj`，`agree` 会按当前节点局部推导。
- 这意味着外部 PMS 没有传完整 `nextStep` 时，plant3d 前端仍可能自行补全 `assigneeId/name/roles` 后调用 `workflow/sync`。

影响：

- 当前默认已是外部流程驱动，流程目标节点和办理人应完全由 PMS 通过 `workflow/sync` 入参提供。
- 前端 fallback 会让“外部系统事实源”变成“外部入参 + plant3d 本地推导”的混合模式，出问题时很难判断责任边界。
- 如果本地 `currentTask` 滞后，fallback 推导出的 `nextStep` 也可能是旧节点上的错误结果。

建议：

- 外部模式下取消本地 `nextStep` 推导：`active` / `agree` / `return` 需要流转时必须由 PMS 传 `nextStep`。
- `payload.targetNode` 可以仅作为诊断字段，不应用来补全 `assigneeId`。
- 缺少 `nextStep` 时前端应明确返回 `missing_external_next_step`，提示 PMS 补全 sync 入参。

### P2：历史文档曾声明 `sync return` 会做 annotation_check，与当前代码相反

证据：

- `WORKFLOW_VERIFY_V3_BREAKING_NOTICE.md` 原写“sync return 是，会阻断无问题驳回”（已在本轮更新为当前契约）。
- v3 初版验证报告记录了旧 return 批注门禁结果，已从当前文档集删除，避免误导接入方。
- 当前 `validate_workflow_return()` 已无 `evaluate_annotation_check()` 调用。
- `verify_action_intent_for_node()` 对 `return` 返回 `None`，即 verify 也跳过批注检查。

影响：

- PMS 接入方和后续维护人员如果看到历史报告，仍可能按旧规则排查问题。
- “驳回不需要检查批注情况”的新契约需要以新架构说明和 PRD 为准。

建议：

- 保持新架构说明、PRD、breaking notice、HTTP 示例和 PMS 联调文档一致。
- 增加回归用例：`return` 在无 open/rejected 批注时 verify/sync 均不触发 annotation_check。

## 已确认的正向点

- 默认前端模式已经是 external：`resolveWorkflowMode()` 在未启用内部模式 feature 时直接返回 `external`。
- 设计侧发起面板在 external 模式下只保存编校审单数据，不再内部提交。
- `return` 当前后端代码已经跳过 annotation_check，符合“驳回不需要检查批注情况”的最新诉求。
- `ReviewPanel.vue` 的 `clearDraftData` 参数已与 `confirmCurrentDataSafely()` 对齐，之前的 `t.clearDraftData is not a function` 风险点已修复。

## 建议整改顺序

1. 先定 external 权限边界：是完全信任 PMS，还是 token claims/owner 双校验。
2. 加 postMessage origin 白名单，避免外部 iframe 消息被任意来源触发。
3. 修复 `applyExternalWorkflowChange()` 成功后的本地 `currentTask` 刷新。
4. 移除 external bridge 的本地 `nextStep` fallback，要求 PMS 显式传入 sync 流转目标。
5. 更新测试，特别是 `return` 跳过 annotation_check 的新契约。
