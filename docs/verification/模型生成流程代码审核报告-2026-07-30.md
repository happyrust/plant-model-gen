# 模型生成流程代码审核报告（2026-07-30）

## 审核范围

`plant-model-gen` 的模型生成链路，从入口到落锚：

- 入口：`incremental-sesno` / `watch-incremental` / `model-version catch-up` / web 生成接口
- 编排：`version_management/increment_run.rs`、`model_gen_catchup.rs`、`model_generation_run.rs`
- 读取：`generation_read/`（读取契约、as-of 切面、层级快照、目录闭包）
- 生成：`fast_model/gen_model/`（orchestrator、gen_pipeline、write_pipeline）
- 门控：`version_management/model_impact.rs`、`versioned_db/model_gen_debt.rs`

未逐行审核几何算法本体（`mesh_generate.rs`、`cata_model.rs`、`prim_model.rs`、
`room_model.rs`、`manifold_bool.rs`）。

## 结论

骨架扎实：读取切面绑定、run 台账（append-only + 确定性 record id + 幂等/冲突检测）、
欠账-水位模型、属性影响门控这几层设计和测试都到位。

主要问题集中在**执行层的 fail-open**：多处失败被日志吞掉后仍以成功收尾，
使 `finalize_model_generation` 推进 model_gen 锚点并消费欠账。这直接违反
`CONTEXT.md` 中「模型生成水位只在生成及后处理全部成功后推进」的定义，
且因为欠账已消费，缺失的几何**不会在下一轮增量被重试**。

本轮已闭合全部 fail-open 与性能/卫生项，剩余 1 项为独立中型工程。

### 关于第 7 条的更正

初判为「调用方带 `--dbnum` 会让目录闭包读不到、报 `MissingRequiredData`」。复核读取
实现后不成立：`load_pe_rows_by_refnos` 按 record id 查、不带 dbnum 过滤，增量路径走
`HierarchySnapshot::load_for_refnos`（由 refno 驱动），`CatalogResolver` 同样按 refno
解析。manifest 的 dbnum 集合不限制跨库目录读取，只影响 `read_at` 选取与全量加载路径。

强行放宽读取切面反而会让 `--allow-full-regen` 的定点修复从「只加载目标库层级」变成
「加载全项目层级」。因此只补注释说明这里用原始 options 是刻意的。

### 关于第 10 条的更正

`defer_db_write` 已在解析层整体退役：`options::parse_defer_db_write` 恒返回 false，
CLI `--defer-db-write` 只打印忽略提示。原先的硬编码与之一致，不是配置被静默覆盖。
改为从 `db_option` 读取（行为不变），与同文件 `init_model_tables` 处的判据同源。

该退役开关目前仍留有四处面子：`DbOption::defer_db_write` 字段、
`BooleanBridgeRequest::defer_db_write` 字段、CLI flag、解析器桩。清理属独立收尾。

## 行为变化

### 从「降级继续」变为「硬失败」

以下八处此前失败后继续执行，现在会中止本次生成：

1. BRAN `cata_hash_map` 构建
2. BRAN tubing 生成
3. CATE 页 `cata_hash_map` 构建
4. 生成预检查
5. Web Bundle 导出
6. instances.json 导出
7. 增量子树 `pe_transform` 失效
8. 删除节点 `pe_transform` 清理

在增量 / catch-up 链路上，这意味着 `catch_up_model_generation_with_lock` 返回 `Err`
→ `increment_run` 记 failure → **不发 model_gen 锚点、不消费欠账**，欠账留待下轮重试。

预检查一项经确认不会把原本能跑的站点变成失败：`check_db_meta_info` 加载失败在
`run_precheck` 内部已降级为 `Ok`，`check_tree_files` 已是 no-op，生成入口把
`pe_transform_mode` 固定为 `Skip`（L0），L1/L2 的刷新失败路径走不到。

### 新的 HTTP 状态码

`api_show_by_refno` 在抢锁失败时返回 **409**，语义是「另有写者正在跑，稍后重试」。
前端若只处理 200/500，需要补一条分支，否则会表现为不明所以的报错。

### 并发拒绝

web 生成接口现在与 CLI 的 `watch-incremental` / `incremental-sesno` 互斥。
`ProjectMutationLock` 是 `try_lock_exclusive`（非阻塞），冲突时立即失败，
不会挂起请求。锁按项目粒度（`output_root/<project>/incremental.lock`），
多站点之间不互相影响。

## 验证要点

无法用 `cargo test` 验证（仓库规约禁止）；以下按实际运行验证。

### 1. 灰度一轮增量

在**单个**站点跑一轮 `watch-incremental`，重点看是否突然报出以前被掩盖的存量问题：

- `build_cata_hash_map_from_session` 失败（常见诱因：缺 db_meta / tree 文件的老站点）
- `pe_transform` 失效失败

若报错，说明这些静默缺口一直存在，需要按站点排查而不是回退改动。

### 2. 确认失败不再推进水位

制造一次生成失败（例如临时把 meshes 输出目录设为不可写触发 Web Bundle 导出失败），
然后检查：

- `sesno_version_anchor` 中该 dbnum 的 `source='model_gen'` 锚点**未**推进
- `model_gen_debt` 中对应区间**仍在**
- `model_generation_run` 有 `started` + `terminal(failed)` 两条事件

### 3. 并发互斥

- CLI 起 `watch-incremental`，同时调 `POST /api/model/show-by-refno` → 应得 409
- 反向：web 生成进行中起 CLI 增量 → 应得「项目写入锁已被占用」并带 `web:<endpoint>` holder
- SSE 流生成中断开客户端 → 锁应释放（再起一次 CLI 增量能抢到）

### 4. 错误分类

确认一次真实的 retention 过期仍被识别为 `HistoryExpired`（站点若配了有限
`version_retention`，查一个窗外 sesno 即可），而一个故意写错的查询报的是
`BackendQuery` 而非 `HistoryExpired`。

### 5. 输出路径

配置了自定义 `output_root` 的站点，跑一次生成后确认 perf 报告落在
`<output_root>/<project>/profile/` 而不是 `./output/`。

## 未处理项

### 第 4 条：目录反向波及闭包仍是 shadow

`increment_run.rs` 中 `compute_catalogue_reverse_shadow` 只观测，summary 里明写
`"mode": "shadow_only_not_consumed"`。后果：改一个 SCOM 的几何，引用它的设计实例
不会进生成目标，但数据锚点和 model_gen 水位照常推进 —— **模型静默陈旧**。

`CONTEXT.md` 已把「目录反向波及闭包」写成生效术语，实现仍停在 ADR-0011 P2。
这是剩余项里唯一会直接造成模型陈旧的，建议单独立项。

### 第 8 条的残余

`compute_room_relations_sync` 与 `rebuild_room_relations_only` 两个房间接口，
同样能经 `pregen_room_panels_into_model_cache` 间接进生成管线，目前无锁。
它们不在 `execute_room_regenerate` 的调用链上，因此在各自 handler 层加锁是安全的。

注意：**锁不能下沉到 `gen_all_geos_data` 内部**。`lib.rs`、`run_generate_model`、
`run_regen_model`、`run_increment`、`catch_up_model_generation` 进来时已持有同一把锁，
而 `try_lock_exclusive` 对同进程的第二个文件句柄同样会失败。同理，
`room_model.rs` 的 `pregen_room_panels_into_model_cache` 不能加锁 ——
`execute_room_regenerate` 的阶段 3 会经它再次进入生成管线。
