# Facts

- The MVP deploys existing managed project sites only; it does not accept arbitrary standalone database packages.
- The MVP targets Ubuntu 22 and CentOS 7.9 Linux hosts; Windows is excluded from MVP execution and remains a later adapter phase.
- CentOS 7.9 support may only be described as complete after a real CentOS 7.9 remote smoke deployment passes.
- The local admin UI defaults to the offline deploy page and guides users to create or parse a managed site when no deployable site exists.
- The offline deploy page is the main user entry point; site detail pages reuse the same deploy wizard component or navigate to it.
- SSH credentials may be stored in SQLite as plain text during the current test phase.
- Remote deployment supports root users, sudo-capable users, and ordinary users without sudo.
- When a remote user cannot perform privileged operations, the deployment skips system-level steps instead of failing solely for lack of privilege.
- A full deployment registers and starts system services when root or sudo privileges are available.
- A degraded user-mode deployment starts remote processes with generated start, stop, and status scripts plus pid and log files under the remote site directory.
- A degraded user-mode deployment does not promise boot-time auto-start or automatic firewall configuration.
- The MVP uses overwrite-style deployment first, while artifact and release-directory deployment is a required follow-up phase.
- Redeploying the same site to the same target is supported and only stops services or processes managed by this deployer.
- The deployer never silently changes remote web or database ports; occupied ports block preflight with a clear message.
- The required deploy payload includes the managed site's SurrealDB/RocksDB data directory, web_server binary, SurrealDB binary, resource/surreal scripts, and viewer/admin static resources.
- Mesh, asset, parquet, and cache directories are detected and surfaced as deploy warnings or requirements before they become automatic payloads.
- Remote deploy status remains site-scoped for MVP but is associated with the submitted admin task id or deploy id.
- The UI distinguishes full deployment success from degraded deployment success.
- MVP completion requires real remote smoke verification through a running web_server and HTTP or POST API checks; cargo tests are not part of verification.
- A successful remote smoke verifies remote /api/status, database connection check, /api/site/identity, and viewer static resource access.
- A deployed remote web_server is treated as a managed site agent that can report status after installation.
- MVP monitoring uses local pull-based status checks, while long-term central heartbeat management is reserved for a later phase.
- Remote agent identity includes a simple site_token field, accepted as plain-text test-phase configuration.
- A thin remote or site agent API is introduced separately from remote target configuration and remote sync workflows.
- Upgrade and full data snapshot sync are planned follow-up capabilities and are not required for MVP deployment completion.
